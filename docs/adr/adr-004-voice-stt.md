# ADR-004: Голосовой ввод в диалог (STT)

| Поле | Значение |
|------|----------|
| Статус | Принято |
| Дата | 2026-05-08 |

## Контекст

Нужен сценарий «голосом к ассистенту» в веб-клиенте и в Telegram. Ядро — backend: единая бизнес-логика диалога и LLM уже есть; не хватает преобразования речи в текст.

## Рассмотренные варианты

1. **Потоковый STT в браузере + только текст в API** — меньше нагрузки на backend, но два контура (Web Speech API vs Telegram), сложнее согласовать качество и политику логирования.
2. **Отдельный микросервис STT** — гибко, но избыточно для MVP.
3. **Один endpoint в backend: загрузка аудио → STT (Whisper) → существующий сценарий диалога** — один pipeline для веба и бота, KISS.

## Решение

- STT: **OpenAI Whisper** (`whisper-1`) через официальный `openai` Python SDK; ключ **`OPENAI_API_KEY`** (отдельно от OpenRouter для чата).
- HTTP: **`POST /v1/voice/dialog-messages`**, `multipart/form-data`: поле `audio` (файл) + `flow_id`; для бота дополнительно `telegram_user_id`; для веба — авторизация JWT, `participant_id` берётся из токена.
- Ответ: как у текстового диалога, плюс поле **`transcription`** (распознанный текст пользователя).
- Лимиты: размер файла по умолчанию **≤ 25 MB** (ограничение Whisper API); содержимое аудио и текст транскрипта **не пишутся в логи** (политика `docs/vision.md`); допустимо логировать `user_id` / `participant_id`, размер файла, длительность (из метаданных клиента при наличии).

## Последствия

- Для включения голоса в проде нужен действующий `OPENAI_API_KEY` с доступом к Audio API.
- Стоимость и латентность — по тарификации OpenAI; при отсутствии ключа endpoint возвращает ошибку конфигурации (503 или аналог).
- Альтернативные регионы/модели STT потребуют нового ADR при смене провайдера.
