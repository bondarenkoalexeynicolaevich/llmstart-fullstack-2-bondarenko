# ADR-005: Ответы по данным потока (Text-to-SQL / аналитика)

**Статус:** Принято  
**Дата:** 2026-05-08

## Контекст

Преподавателю нужны ответы на уточняющие вопросы по метрикам потока (сдачи, студенты, занятия) без ручного SQL и без усложнения дашборда. Вариант «LLM генерирует произвольный SQL» повышает риски инъекций, сложнее валидация и аудит.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|--------|--------|--------|
| **A.** LLM → произвольный SQL, read-only роль БД | Максимум гибкости | Нужна жёсткая санация, борьба с DDL/DML-токенами, утечка схемы в промпт |
| **B.** LLM классифицирует запрос → набор параметрических SELECT (allowlist шаблонов) | Детерминированные запросы, без динамического SQL из текста пользователя | Только поддержанные типы вопросов |
| **C.** Полностью rule-based без LLM | Простота | Хуже понимание свободной формулировки |

## Решение

Принят **вариант B**: один вызов LLM возвращает **только** JSON `{"intent": "<allowlist>", "params": {...}}`. Backend выполняет заранее описанный безопасный запрос через SQLAlchemy (параметризованные выражения, без сборки строки SQL из пользовательского ввода).

- Доступ: **JWT веб-сессии**, только роль **`teacher`**, путь включает `flow_id`, совпадающий с токеном.
- Ответ включает `correlation_id` для поддержки и логирования (**без** логирования текста вопроса пользователя).
- Интент `questions_count_by_lesson` для MVP считает **число сдач** (`Submission`) по конкретному занятию (пара `module_order`, `lesson_order`) как понятную метрику активности по уроку, а не «чат-вопросы» без привязки к урокам в данных.

При необходимости расширения сценариев добавляются новые intent + шаблоны; переход на вариант A — отдельный ADR.

## Последствия

- Предсказуемое время ответа и поверхность атак меньше, чем у свободного Text-to-SQL.
- Неподдержанные формулировки дают ошибку клиента (`UNRECOGNIZED_INTENT`) и просьбу переформулировать.
- Документация API и описание intent поддерживаются вручную в sync с кодом backend.
